# FitnessAI PRD 未决项对账

## 1. 范围与 Gate 结论

本次只读对账比较了 `prd.md`、`prd.zh-CN.md`、`addendum.md`、`addendum.zh-CN.md` 和 `.memlog.md`，核查显式未决标记、memlog 中尚未解决的假设、MVP 交接阻塞项、编号与交叉引用缺陷，以及双语漂移。

**Gate 结论：**双语文档结构同步，需求编号完整，但 PRD 还不能在不修改的情况下安全定稿或交接。当前仍有 14 个独立未决项，其中 7 个会阻塞 UX、架构或 Epic 验收。

## 5. 双语一致性审计

英文与中文 PRD 都是 262 行，frontmatter 相同，标题层级、顺序列表、需求编号、数值阈值、链接、范围标签和结论均对应一致。两份 addendum 也都是 49 行，标题、来源、技术标识和决策保持一致。未发现实质性双语语义矛盾。

Post-MVP 标签周围使用中文全角标点属于排版本地化，不是编号不一致。解决 OI-01 至 OI-14 中任一问题时，必须在同一次修改中同步更新两个语言版本。

## 6. 阶段阻塞项的最小 Capability-Level 关闭建议

以下 ID 均为建议新增的稳定 ID。不得重新编号现有 ID。即使新 ID 的全局编号高于相邻需求，也应将它放入指定的能力分组。

### OI-01 — 自动识别发布契约

- **建议插入位置：**新增 `FR-061`，放在第 7.2 节 FR-015 后；在 PRD 中新增 `8.5 识别质量与发布验收` 小节，包含 `NFR-REC-001` 和 `NFR-REC-002`。
- **FR-061：**“每个版本都必须声明动作识别、次数统计和正式组检测所支持的动作、Apple Watch 系列、OS 范围和信号条件。在声明范围之外，FitnessAI 必须拒绝自动判断，并保留手动记录路径。”
- **NFR-REC-001：**“在查看留出结果前，必须在版本化发布验收档案中冻结初始动作识别、次数统计误差、正式组边界误差、拒绝估算/risk coverage，以及必测动作、设备和冷启动切片各自的阈值。”
- **NFR-REC-002：**“只有全部冻结阈值均通过，且共同主动打断预算仍然满足时，自动识别能力才能发布；纠错和数据挽救成功必须单独报告，不得改善初始识别结果。”
- **解除阻塞的原因：**UX 获得明确的拒绝判断/手动兜底路径，架构获得有边界的支持范围，Epic 获得版本化且不会污染留出结果的发布 Gate，同时 PRD 无需规定具体模型实现。

### OI-02 — 完整的用户权威纠错闭环

- **建议插入位置：**新增 `FR-062` 和 `FR-063`，放在第 7.2 节 FR-014 后，并从 FR-041 交叉引用。
- **FR-062：**“在活动训练会话中以及已完成训练历史中，用户可以纠正动作、次数、实际重量、RPE 状态、训练组顺序或边界；补充缺失的实际训练组；并删除错误的实际训练组。每次纠错必须保留所有未受影响的字段和可审计纠错历史。”
- **FR-063：**“FitnessAI 在结束前识别未解决或缺失字段。用户可以明确选择保留未解决状态并结束；此时训练会话必须保持明显的不完整状态，并可重新打开纠错；只有所有必需的已记录项目得到解决后，训练会话才变为完整。”
- **解除阻塞的原因：**UX 可以设计所有事实恢复状态，架构可以定义可靠可编辑实体和审计历史，Epic 可以针对所有捕捉字段验证完整度，而不再只覆盖动作标签纠错。

### OI-03 — 活动训练会话故障恢复

- **建议插入位置：**新增 `FR-064`，放在第 7.1 节 FR-007 后；新增 `NFR-RECOV-001`，放在第 8.3 节 NFR-SESSION-004 后。
- **FR-064：**“App 进程、设备、传感器或连接中断后，FitnessAI 必须提供从最新可靠状态恢复同一个进行中训练会话的能力。无法恢复时段的信息保持明显待确认，绝不能被推断为已确认。”
- **NFR-RECOV-001：**“重启、重连、同步重试和会话恢复不得重复、丢失或打乱已经可靠确认的实际训练组，也不得覆盖更新的用户纠错。真机恢复测试必须覆盖 Watch 进程终止、设备重启、Watch–iPhone 断连、后端不可用和传感器信号缺失。”
- **解除阻塞的原因：**UX 获得确定的恢复与待确认数据体验，架构获得必须保持的恢复不变量，Epic 获得覆盖产品首要可信承诺的明确故障场景。

### OI-04 — 支持界面与设备拓扑

- **建议插入位置：**新增范围小节 `6.3 支持的产品界面`，包含 `FR-065` 和 `FR-066`；在新小节 `8.6 兼容性` 中新增 `NFR-COMPAT-001`。
- **FR-065：**“计划训练或自由训练会话在 Apple Watch 上可用后，即使 iPhone 或后端无法实时连接，用户仍可开始、记录、纠正和结束训练。需要 iPhone 的功能必须在用户进入 Watch 流程前明确指出。”
- **FR-066：**“用户在受支持的 iPhone 上建立 FitnessAI 账号，并将受支持的 Apple Watch 与该账号关联。关联后，Watch 在离线状态下仍可基于最近一次已认证账号状态继续本地训练记录。”
- **NFR-COMPAT-001：**“每个版本必须声明最低支持的 iPhone、Apple Watch、iOS 和 watchOS 版本及受支持配对组合。UJ-1、UJ-3 和 UJ-5 必须在每一种声明配对上通过。”
- **解除阻塞的原因：**UX 明确认证由哪个界面负责，以及哪些流程必须在手机不在场时继续；架构可以划分设备职责和连接边界；Epic 可以面向有限兼容矩阵执行。

### OI-05 — 隐私、安全与中国区数据治理

- **建议插入位置：**在 PRD 中新增 `8.7 隐私、安全与数据治理` 小节，包含以下稳定 ID。
- **NFR-PRIV-001：**“账号资料、训练历史、实际训练组、RPE 来源、分析输入和个人模型摘要只有在用户明确知情同意后才能同步。完整高频传感器流默认仅保留在本地；任何上传都必须具备另行明确的用途和同意。”
- **NFR-SEC-001：**“账号范围内的数据在传输中和静态存储时都必须受到保护，并且只能由已认证用户、已授权设备和明确授权的服务角色访问。安全故障不得把一个账号的数据暴露给另一个账号。”
- **NFR-PRIV-002：**“上线前，FitnessAI 必须维护一份面向用户且可审查的数据地图，列出每种同步数据、用途、存储和处理区域、保留规则及接收方。禁止未声明的传输或二次使用。”
- **NFR-PRIV-003：**“数据导出和账号删除必须覆盖全部账号范围内的同步数据类别及其常规副本。FitnessAI 必须展示请求状态和完成结果，并披露任何法定保留例外及其时长。”
- **解除阻塞的原因：**UX 获得同意、披露、导出和删除状态；架构获得权威数据边界与访问不变量；Epic 无需规定具体后端技术即可建立可审计的隐私/安全验收。

### OI-06 — 同步与账号生命周期语义

- **建议插入位置：**新增 `FR-067`、`FR-068` 和 `FR-069`，放在第 7.6 节 FR-048 后。
- **FR-067：**“同一账号范围字段在多台设备上被修改时，FitnessAI 必须保留能够确定的最新用户纠错。如果无法安全确定纠错顺序，FitnessAI 必须保留两个候选值并要求用户选择；不得静默丢弃任何候选值。”
- **FR-068：**“跨设备恢复必须以相同稳定身份重建每个已同步训练计划、训练会话、实际训练组、纠错和 RPE 来源，并向用户报告恢复进度和任何未解决故障。”
- **FR-069：**“退出登录或切换账号前，FitnessAI 必须识别未同步的本地信息，并要求用户进行同步、导出或明确丢弃。退出登录不等于删除账号；账号删除遵循 FR-048 和已声明的保留规则。”
- **解除阻塞的原因：**UX 可以设计冲突、进度、失败和退出登录状态；架构获得确定性保全规则和稳定身份不变量；Epic 获得可测试的并发编辑、恢复和账号切换结果。

### OI-07 — 可执行的 RPE 发布与信任 Gate

- **建议插入位置：**新增 `NFR-RPE-011` 和 `NFR-RPE-012`，放在第 8.2 节 NFR-RPE-010 后。
- **NFR-RPE-011：**“在查看留出结果前，版本化 RPE 验收档案必须冻结 RPE 量表与正确性容差、符合条件估算的定义、相对每个已声明基线的最低参与者留出与后续会话增益、校准与 risk–coverage 目标、信号缺失与必测切片标准，以及 SM-INT-001 范围内的最大提示与纠错负担。”
- **NFR-RPE-012：**“除非完整验收档案通过，否则 RPE 自动采用必须保持不可用。该档案必须定义漂移和重新验证触发条件；发布测试必须验证每个低置信度、陌生、信号缺失或漂移案例都采用待确认或有限确认兜底路径。”
- **解除阻塞的原因：**UX 获得确定的临时值、自动采用、纠错和重新验证状态；架构获得评估与兜底契约；Epic 可以依据冻结证据控制发布，而不再依赖‘稳定’或‘不可接受’等主观术语。

## 7. 建议关闭顺序

1. 在 UX、架构或 Epic 交接前解决 OI-01 至 OI-07。
2. 为 OI-08 至 OI-13 指定负责人和重访条件；OI-11 可以继续明确延后至 Post-MVP。
3. 在结构润色阶段修复 OI-14，然后重新运行编号与双语一致性检查。
4. 只有完成以上关闭后，才运行正式 PRD Reviewer Gate，并同步将两份 PRD 设置为 `status: final`。

## 8. 结论

双语 PRD 已同步，不存在字面占位符或损坏的需求编号。当前仍有 **14 个未决项**，其中 **7 个阶段阻塞项**。主要阻塞点是缺失的识别验收契约、不完整的纠错与失败恢复流程、未定义的支持设备拓扑、缺少隐私/安全/数据治理 NFR、同步语义规定不足，以及不可执行的 RPE 发布 Gate。
